This page shows where the settings of a self-hosted Claude Managed Agents server go, and lists them. To set up a feature, see [Single sign-on](https://platform.claude.com/docs/en/managed-agents/self-hosted/configure), [Agent identity and credentials](https://platform.claude.com/docs/en/managed-agents/self-hosted/agent-identity), and [Inference provider](https://platform.claude.com/docs/en/managed-agents/self-hosted/inference-provider).

## Where settings go

The server reads its settings from one YAML file, and its credentials from its environment.

* **Docker Compose:** The file is `compose.config.yaml`, beside `docker-compose.yml` in the extracted archive. Edit it, then run `docker compose restart cma-server` from that directory.
* **Kubernetes:** The file is the `server.config` value of the server Helm chart. Edit it in your values file, run `helm upgrade`, and then restart the servers with `kubectl -n cma-server rollout restart deployment -l anthropic.com/role=server`. See [Deploy on Kubernetes](https://platform.claude.com/docs/en/managed-agents/self-hosted/kubernetes).

If the server rejects a setting that the self-hosted pages show, [upgrade the server](https://platform.claude.com/docs/en/managed-agents/self-hosted/upgrade). `cma-server.example.yaml`, at the top of the archive, annotates the common keys.

Credentials never go in the file. The server reads them from environment variables, or from the identity that your cloud attaches to the host.

### Pass a credential to the Compose stack

In the Compose stack, the server container receives only the variables in the `environment:` list of the `cma-server` service in `docker-compose.yml`. To pass another one:

1. Add its name to that list, and set its value in `.env`.
2. If the credential is a file, put the file beside `docker-compose.yml`, and add a line such as `- ./gcp-key.json:/etc/cma-server/gcp-key.json:ro` to the `x-server-mounts` list in `docker-compose.yml`. The path after the first colon is the file’s path inside the container. Use that path as the variable’s value in `.env`, or as the value of the setting that names the file.
3. Run `docker compose up -d`. A restart doesn’t reread `.env`.

An upgrade replaces `docker-compose.yml`, so repeat these edits in the new release’s file before you start its stack.

## How to read the tables

Each setting has a key in the [settings file](https://platform.claude.com/docs/en/managed-agents/self-hosted/configuration-reference#where-settings-go), and most settings also have an environment variable. A variable overrides the file, and the file overrides the default. The server doesn’t start if its settings file has an unknown key, and the error says where the key is.

* **Keys:** Each dot in a key is a level of nesting in the file. For example, `server.addr` is the `addr` key in the `server` section.
* **Variables:** A variable’s name is `CMA_` and then the key in capitals, with two underscores in place of each dot.
* **File only:** The setting has no variable.
* **Environment only:** The server doesn’t start if the setting is in the file.
* **`bedrock` only, and similar labels:** The setting works only with that provider, store, or secret manager. If you set it while you use a different one, the server doesn’t start.
* **Lists:** A list is a YAML list in the file, and a comma-separated string in a variable.
* **Durations:** A duration is a number with a unit, such as `30s`, `5m`, or `1h`.
* **Integers:** An integer is plain digits, with no sign, leading zero, or underscore.

At startup, the server logs the settings that you set and most defaults, each with where its value came from, such as `server.addr=0.0.0.0:8400 (file)`. It logs `***` in place of a secret, except a server API key that it generated itself.

## Git repositories

See [Git repositories need an allowlist entry](https://platform.claude.com/docs/en/managed-agents/self-hosted/differences#git-repositories-need-an-allowlist-entry).

| Setting<br />Environment variable                                           | Default                 | Description                                                                                                                                                                                                                                                                                                           |
| --------------------------------------------------------------------------- | ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `git.allowed_hostnames`<br />`CMA_GIT__ALLOWED_HOSTNAMES`                   | None                    | The Git hosts that a session’s repositories can be on. Hostnames match exactly, with no wildcards, and an entry doesn’t cover its subdomains. An entry allows port 443, or the one port that it names, as in `git.example.com:8443`. Without this setting, the server accepts no repositories.                        |
| `git.private_hostnames`<br />File only                                      | None                    | The hostnames from `git.allowed_hostnames` that resolve to a private address, written without a port. For any other hostname, the server connects only to its public addresses.                                                                                                                                       |
| `git.allowed_push_refs`<br />`CMA_GIT__ALLOWED_PUSH_REFS`                   | None                    | The branches that agents can push to, each under `refs/heads/`. An entry that ends in `/` allows every branch under it. Any other entry allows that one branch. Without this setting, agents can’t push.                                                                                                              |
| `git.commit_author_name`<br />`CMA_GIT__COMMIT_AUTHOR_NAME`                 | `Claude`                | The author name on the agent’s commits. Set it together with `git.commit_author_email`.                                                                                                                                                                                                                               |
| `git.commit_author_email`<br />`CMA_GIT__COMMIT_AUTHOR_EMAIL`               | `noreply@anthropic.com` | The author email address on the agent’s commits. Set it together with `git.commit_author_name`.                                                                                                                                                                                                                       |
| `git.max_concurrent_transfers`<br />`CMA_GIT__MAX_CONCURRENT_TRANSFERS`     | `32`                    | The most Git requests that one server carries at once. The minimum is `1`.                                                                                                                                                                                                                                            |
| `git.max_session_transfer_bytes`<br />`CMA_GIT__MAX_SESSION_TRANSFER_BYTES` | `8589934592` (8 GiB)    | The most Git traffic, in bytes, that one server carries for one session, uploads and downloads together. The count restarts at zero each time a sandbox picks up the session. At the limit, the server refuses the session’s next Git requests with a `403`. `0` means no limit. Otherwise, the minimum is `1048576`. |
| `git.max_push_bytes`<br />`CMA_GIT__MAX_PUSH_BYTES`                         | `2147483648` (2 GiB)    | The most bytes that one push can send. The minimum is `1048576`.                                                                                                                                                                                                                                                      |

These limits apply to Git repositories:

* **Protocols:** The server doesn’t support SSH or Git LFS, and it refuses redirects, such as the one for a renamed repository.
* **Tokens:** The Git host must accept the token as the password of HTTP Basic authentication, under the username `x-access-token`.
* **URLs:** A repository URL has one owner and one repository name, so you can’t use a repository in a GitLab subgroup.
* **Hosts:** For a URL on a host that `git.allowed_hostnames` doesn’t list, the server returns a `400`. The error message says that the URL must be on `github.com`, even if you list other hosts.
* **Pushes:** The server always refuses a push that deletes a branch, or that changes anything other than a branch, such as a tag.
